Guia prático · ASP.NET Core MVC

CRUD de usuários do jeito certo: DTO, SOLID e SRP na prática

Você vai sair de um controller que faz tudo para uma arquitetura em camadas: o controller só fala HTTP, o service cuida das regras e os DTOs controlam o que entra e o que sai. Sem mágica, com código que você consegue testar.

01

Visão geral: cada peça com um único trabalho

O mapa mental antes de escrever a primeira linha.

CRUD é só Create, Read, Update e Delete. A dificuldade não está nas quatro operações — está em onde colocar cada responsabilidade. É aí que entram DTO, Service e SOLID.

1 · HTTP Controller recebe o DTO, valida e devolve a View
→
2 · Regras Service decide, orquestra e valida e-mail único
→
3 · Dados DbContext consulta e grava com EF Core
→
4 · Storage SQLite tabela Usuarios

Na volta, o service entrega um UsuarioResponseDTO. A entidade do banco nunca chega na View.

A regra de ouro

✓
Controller não sabe SQL. Service não sabe HTTP. Entidade não sabe validação de formulário.

Se você conseguir repetir essa frase, metade do caminho está feito.

Quem faz o quê

Peça Responsabilidade Não pode
Controller Receber a requisição, checar o ModelState, chamar o service e decidir a resposta (View, Redirect, NotFound). Regra de negócio, acesso a banco, hash de senha.
Service Executar as regras do caso de uso: e-mail único, hash, orquestração do CRUD. Saber o que é IActionResult, View ou HTTP.
DTO Definir o contrato de entrada e saída. Carregar só o que o caso de uso precisa. Regra de negócio ou acesso a banco.
Entidade Representar a tabela do banco e o que o EF Core mapeia. Ser usada como modelo de formulário ou de resposta.
DbContext Falar com o banco através do EF Core. Conter regra de negócio.
02

Estrutura de pastas

Uma pasta por responsabilidade. O nome já diz onde a coisa mora.

No projeto, a entidade Usuario.cs fica em Models/ com o namespace CompleteSystem.Models. A regra é simples: o namespace acompanha a pasta. Se a entidade estiver em Models/, o namespace deve ser CompleteSystem.Models, nunca CompleteSystem.Data.

Ordem de leitura do fluxo

Entidade → DTOs → DbContext → interface do service → service → mapper → controller → views. Cada peça depende apenas da peça anterior.

03

A entidade: o espelho da tabela

Simples de propósito. Ela só representa os dados que o banco guarda.

A entidade é a classe que o Entity Framework mapeia para a tabela Usuarios. Ela não valida formulário, não formata data e não sabe nada de HTTP. Repare que o campo de senha se chama SenhaHash: a senha pura nunca é persistida.

!
Nunca guarde a senha em texto puro

O service vai transformar a senha em hash antes de salvar. Se um dia o banco vazar, ninguém consegue ler as senhas originais.

04

DTOs: o contrato de entrada e saída

DTO é a forma dos dados que atravessam a fronteira da sua aplicação.

DTO significa Data Transfer Object. Ele existe para transportar dados entre o mundo de fora (formulário, JSON) e o mundo de dentro (service). Separar entrada, atualização e resposta evita aceitar campos que o usuário não deveria mandar — o famoso mass assignment / over-posting.

DTO Onde é usado Campos
UsuarioCreateDTO Formulário de criação e action Create Nome, Email, Senha
UsuarioUpdateDTO Formulário de edição e action Edit Id, Nome, Email, Ativo
UsuarioResponseDTO Listagem, detalhes e retorno do service Id, Nome, Email, Ativo, CriadoEm

Por que não devolver a entidade?

  • Segurança: a entidade tem SenhaHash; o DTO não.
  • Contrato estável: mudar uma coluna do banco não quebra a tela automaticamente.
  • Validação no lugar certo: [Required] e [EmailAddress] ficam no DTO, não na entidade.
  • Sem over-posting: o formulário só consegue preencher os campos que o DTO declara.
!
DTO é classe, não interface

DTO é uma classe de transporte: não existe “interface de DTO”. Interfaces seguem outro papel e outra convenção de nome — IUsuarioService, por exemplo. O prefixo I é para interfaces, não para DTOs. Se aparecer um UsuarioInterfaceDTO, é sinal de nome e responsabilidade confusos: renomeie ou remova.

✓
Validação em dois níveis

DataAnnotations no DTO validam formato (campo vazio, e-mail inválido). O service valida regra de negócio (e-mail já cadastrado, usuário inexistente). Cada um no seu quadrado.

05

DbContext: a ponte com o banco

Um lugar só para configurar o mapeamento e falar com o SQLite.

O AppDbContext expõe a tabela Usuarios e configura tamanho de campos, obrigatoriedade e o índice único de e-mail. Esse índice é a última linha de defesa contra e-mails duplicados, mesmo se duas requisições chegarem ao mesmo tempo.

i
Um DbContext por requisição

O EF Core registra o AppDbContext com tempo de vida scoped: uma instância por requisição HTTP. Não crie new AppDbContext() na mão — peça no construtor.

06

A interface do service

O contrato que o controller conhece. A implementação fica escondida.

A interface existe para o controller depender de uma abstração, e não da classe concreta. Isso é a base da Inversão de Dependência (o D do SOLID) e o que permite trocar a implementação por um mock em testes.

Três detalhes importantes do contrato:

  • Todos os métodos são assíncronos (Task), porque o banco é I/O.
  • O retorno é DTO, nunca entidade e nunca IActionResult.
  • Consultas que podem não achar nada retornam nullable (?) ou bool. Quem decide o NotFound é o controller.
07

O service: onde a regra de negócio mora

Todo o CRUD em um lugar testável, sem uma linha de HTTP.

O service recebe o AppDbContext e o IPasswordHasher<Usuario> pelo construtor. Ele não sabe que existe formulário, View ou IActionResult. Quando uma regra é violada, ele lança uma exceção de negócio — e o controller traduz isso para o usuário.

O que cada método faz

  • ListarAsync: busca todos, ordena por nome e mapeia para DTO. O AsNoTracking() avisa ao EF que ninguém vai alterar esses objetos — é mais leve para leitura.
  • ObterPorIdAsync: retorna null quando não encontra. Quem transforma isso em NotFound() é o controller.
  • CriarAsync: verifica e-mail duplicado, normaliza nome/e-mail, gera o hash, salva e devolve o DTO de resposta.
  • AtualizarAsync: procura o usuário, verifica e-mail duplicado ignorando o próprio id, atualiza e devolve true/false.
  • RemoverAsync: procura, remove e devolve true/false.
✓
Teste de SRP: descreva a classe em uma frase

“UsuarioService executa as regras de negócio do CRUD de usuários.” Uma frase, um motivo para mudar. Se você precisar de “e” (“valida e envia e-mail e gera relatório”), já são responsabilidades demais.

i
Sem HTTP aqui dentro

Repare que não existe IActionResult, ViewBag nem TempData. Isso permite chamar o mesmo service de um controller MVC, de uma API ou de um teste unitário sem mudar nada.

08

Mapper: entidade ↔ DTO sem repetição

Métodos de extensão pequenos, explícitos e fáceis de achar.

O mapeamento é manual de propósito: para um CRUD pequeno, um método de extensão é mais simples de entender do que uma biblioteca inteira. Se um dia os mapeamentos crescerem muito, aí sim vale avaliar o AutoMapper.

Com isso, o service chama usuario.ToResponseDTO() e o controller chama usuario.ToUpdateDTO() no Edit. Se um campo novo aparecer na entidade, você altera o mapper em um lugar só.

!
Não mapeie senha

O mapper de resposta não copia SenhaHash. É exatamente esse detalhe que impede o hash de vazar na listagem ou no JSON de uma futura API.

09

Controller magro: só coordena

Recebe, valida o ModelState, chama o service e escolhe a resposta.

O controller não tem AppDbContext, não faz hash, não verifica e-mail duplicado. Ele apenas conecta o mundo HTTP ao service. Note que as exceções de negócio são traduzidas para ModelState, que é o lugar onde o usuário vê o erro.

Antes e depois

✕ Controller gordo
[HttpPost]
public async Task<IActionResult> Create(Usuario u)
{
    if (await _db.Usuarios
        .AnyAsync(x => x.Email == u.Email))
        return BadRequest();

    u.Senha = BCrypt.HashPassword(u.Senha);
    _db.Usuarios.Add(u);
    await _db.SaveChangesAsync();

    return RedirectToAction("Index");
}
✓ Controller magro
[HttpPost]
public async Task<IActionResult> Create(
    UsuarioCreateDTO dto)
{
    if (!ModelState.IsValid)
        return View(dto);

    await _usuarioService.CriarAsync(dto);

    return RedirectToAction(nameof(Index));
}

O controller da direita não sabe como o usuário é salvo. Ele só sabe quem chamar. A validação de e-mail e o hash ficaram no service.

✓
Checklist do controller magro

Nenhum _context, nenhum HashPassword, nenhum if de regra de negócio. Só ModelState, chamada ao service, escolha de resposta e mensagens para o usuário.

11

Injeção de dependência: ligando as peças

O controller pede uma interface. O ASP.NET entrega a implementação.

No Program.cs você registra o DbContext, o service e o hasher de senha. A partir daí, o ASP.NET resolve o grafo de dependências automaticamente em cada requisição.

Criar o banco

Com o DbContext configurado, gere a migration inicial. Se o comando dotnet ef não existir, instale a ferramenta uma vez. O Database.Migrate() no Program.cs aplica as migrations automaticamente quando a aplicação inicia — por isso o app.db é criado na primeira execução.

i
Tempos de vida (lifetimes)

Scoped (uma instância por requisição): DbContext e services que usam o banco. Transient (uma instância por resolução): classes leves e sem estado. Singleton (uma para a aplicação inteira): configurações e caches. Na dúvida, use Scoped para o CRUD.

Onde cada princípio aparece no seu CRUD de usuários.

✓
SRP na prática: o teste da frase única

Descreva a classe sem usar “e”. “UsuarioService executa as regras do CRUD de usuários.” Perfeito. “UsuarioController recebe a requisição, valida o formulário, acessa o banco, faz o hash e devolve a View.” Reprovado: são responsabilidades demais no mesmo lugar.

!
SOLID não é sobre ter 50 interfaces

É sobre depender de abstrações e manter cada coisa no seu lugar. Para este CRUD, três DTOs, uma interface e um service já entregam muito valor. Não crie camadas que você não consegue justificar.

13

Erros comuns (e como evitar)

Se algum destes aparecer no seu código, a fronteira vazou.

Controller com _context

Se o controller conhece EF Core, a regra de negócio vazou para a camada HTTP.

Service devolvendo IActionResult

Isso amarra a regra de negócio ao ASP.NET e impede reaproveitar em uma API ou teste.

Entidade na View ou no JSON

Além de acoplar a tela ao banco, SenhaHash pode vazar sem querer.

new UsuarioService() no controller

Quebra a injeção de dependência, dificulta testes e ignora o ciclo de vida do DbContext.

Regra de negócio na View

View é apresentação. Validação de e-mail único e hash de senha não pertencem ao Razor.

Senha em texto puro

Sempre gere hash com IPasswordHasher (ou BCrypt) antes de salvar.

Métodos síncronos no banco

Use async/await e os métodos *Async do EF Core.

Esquecer o antiforgery

Todo POST de formulário precisa de [ValidateAntiForgeryToken] e do Tag Helper no form.

Checklist final

  • O controller não referencia AppDbContext.
  • O service não referencia Microsoft.AspNetCore.Mvc.
  • Nenhuma action retorna entidade; só DTO de resposta.
  • O DTO de criação não tem Id nem Ativo.
  • O DTO de resposta não tem SenhaHash.
  • E-mail duplicado é validado no service e no banco (índice único).
  • As dependências são resolvidas por DI, não por new.
  • Todos os acessos ao banco são assíncronos.
14

Próximos passos

O CRUD está pronto. Agora evolua sem quebrar a organização.

  1. Testes unitários do service Use SQLite in-memory ou um banco de teste para validar e-mail duplicado, criação e remoção. O controller pode ser testado com um mock de IUsuarioService.
  2. Repository pattern Se o service crescer ou você precisar trocar a fonte de dados, crie IUsuarioRepository e mova as consultas do EF para lá. Não faça isso só por fazer.
  3. Result pattern Em vez de exceções para fluxos esperados, retorne um objeto com sucesso/erro. Deixa o fluxo explícito e dispensa try/catch no controller.
  4. FluentValidation Quando as regras de validação passarem de DataAnnotations, centralize-as em validadores por DTO.
  5. API com os mesmos DTOs e service Crie um UsuarioApiController retornando os DTOs. A regra continua no service, sem duplicação.
  6. Paginação, busca e ordenação Evolua o ListarAsync para receber filtros e devolver uma página, em vez de carregar a tabela inteira.

Se quiser refazer do zero, siga esta ordem

  1. Entidade Usuario + AppDbContext + migration.
  2. DTOs de criação, atualização e resposta + mapper.
  3. Interface IUsuarioService e implementação UsuarioService.
  4. Registro no Program.cs (DI + connection string).
  5. Controller magro com as cinco actions.
  6. Views de Index, Create, Edit, Details e Delete.
  7. Teste o fluxo completo: criar, listar, editar, detalhar e excluir.
✓
